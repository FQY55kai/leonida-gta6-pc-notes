# 第三部分　14:00 以后追加：VIctory 对照与 allocator 排查

## 1. 对照项目 `Marvisak/VIctory`（已 clone 到 `D:\victory-ref`）

Rust workspace、GPL-3.0-or-later、2026-11-23 起。同类"把 Xbox Series 版 GTA VI 在 PC 上原生跑"的方案，**进度明显更远**：菜单 30 fps、片头有声、开始界面/存档、加载世界约 50 s、能到第一个任务；世界场景仍暗、0.5–1.8 s/帧。测试机为 RX 6700 XT，作者明确警告**真实 GPU 进世界会挂驱动**，建议 `VICTORY_D3D12_WARP=1` 软件适配器。

**架构差异（最关键）**：VIctory **自建完整 160 槽 Xbox device vtable**（`crates/victory-gpu/src/device.rs`），自己实现每个方法再转发到 host D3D12 对象；Leonida 是"包装 PC ID3D12Device + 按序号转发 + 逐个特例"，所以一直在补 slot 错位。

**可直接复用的事实数据（无需 Rust）**：

| 来源 | 内容 | 对 Leonida 的用途 |
|---|---|---|
| `device.rs` FUNCTIONS 表 | Xbox slot 7/8/9/12/13/14/15/26/36/41/48/61/62/69/70/71/73/74/75/76/**78/79/80/81**/86/108/127/133 的完整语义 | 我们靠 cdb 逐个猜的 slot 字典；**78=set_interval、79=schedule、80=wait、81=statistics 是 Xbox 帧调度 API，不是 PC D3D12 方法** |
| `list.rs` `ALLOCATOR_IIDS` / `LIST_IIDS`(10 个) | Xbox allocator / GraphicsCommandList1–6 的 IID | 补 `is_child_iid`，避免后续 `E_NOINTERFACE` 断言 |
| `signature.rs` `SIGNATURE_IIDS` | `{C36A797C-EC80-4F0A-8985-A7B2475082D1}` | 修正了代码中注释写反的 Data2/Data3 |

## 2. 定位方法的关键教训

之前多轮在游戏代码里设断点不命中，误以为"cdb 对手动映射的代码页无效"。**真相是：断点一直是好的，只是设在了从未被执行的地址上。**

* `bp 0x1424787a7`（公共 epilogue）能命中 → 该页可写
* `bp 0x142478440`（函数入口）不命中 → **该函数没被执行**（并非断点失效）
* `bp 0x14247934c`（CHECK1 分支）不命中 → **CHECK1 当时也没被执行**

**结论**：不要凭静态反汇编猜执行流；先确认"这段代码到底跑没跑"，再设断点。

## 3. 本轮击破的三处失败链（均为静默 `false` → `__debugbreak()`）

| # | 症状 | 根因（实测） | 修复 |
|---|---|---|---|
| 1 | 大初始化函数 `0x142478440` 返回 false | **`XMemVirtualAlloc` 提交了 2×24 GB**，吃光系统提交额度，导致其后的 185 MB 分配失败 | `xmem.cpp`：≥16 GB 的预留只 `MEM_RESERVE` 不提交（游戏只是预留地址空间） |
| 2 | 仍返回 false（前进到下一处） | **游戏调用 `VirtualFree(ptr, size, 0x8002)`**：Windows 规定 `MEM_RELEASE` 时 size 必须为 0，故必然失败；游戏把它读成"内存布局失败" | 新建 `runtime/shims/memory.cpp`：`(MEM_RELEASE && size!=0)` 时改为 `MEM_DECOMMIT` 并返回 TRUE（Xbox 的分段释放语义），size==0 的整块释放仍走 Windows |
| 3 | 仍返回 false | 游戏在**同一地址**重新提交刚释放的段（`XMemVirtualAlloc(0x2835e470000, 0xa00000, …)` → 错误 487 `ERROR_INVALID_ADDRESS`） | `xmem.cpp`：指定地址分配失败时改用 `MEM_COMMIT` 单独提交（地址空间已被保留） |

修复 #2 后，**CHECK1/CHECK2（allocator 池）首次被执行**（日志中 allocator #2–#7 出现在命令列表创建之后）；修复 #3 后，**5 段同址重新提交全部成功**。
